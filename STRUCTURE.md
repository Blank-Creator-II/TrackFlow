## Overview

TrackFlow is a modular WinForms desktop application whose core logic is intentionally separated from the UI. The project uses plain text (`.txt`) files for persistent storage per project rules. Keep business logic inside `Services/` and models (custom variables) inside `Models/`. UI code (WinForms) must only call `Services`.

Goal of this document: make the project readable, safe to modify, and explain where to put things and why.



Project Structure:

### Important clarification (read this before adding files)

- `Program.cs, MainForm.cs and MainForm.Designer.cs` are core entry files and should not be duplicated or casually restructured.
- The folder names (`Models/`, `Services/`, `Utils/`, `Forms/`, `Data/`, `Test Result/`) define **responsibility boundaries**, not a fixed file count.

This means:

- You **ARE allowed** to add new `.cs` files **inside the appropriate folder**.
- You **ARE NOT allowed** to add random logic files at the project root.

#### Examples of valid additions

- Adding a new model:

  - `Models/Employee.cs`
  - `Models/InventoryItem.cs`

- Adding new services:

  - `Services/ExpenseSplitService.cs`
  - `Services/InventoryService.cs`

- Adding helpers:

  - `Utils/CurrencyFormatter.cs`

- Adding new UI screens:

  - `Forms/InventoryForm.cs`

As long as:

- Models stay in `Models/`
- Business logic stays in `Services/`
- UI stays in `Forms/`
- Helpers stay in `Utils/`

…the structure is considered **correct and compliant**.

This rule also ensures that AI-assisted coding tools understand the project layout and place generated files in the correct location.

## High-level architecture

- **Models/**: Simple data objects (POCOs) think of it as custom variables we will use that describe the data shapes.
- **Services/**: Business logic, calculations, data parsing and storage orchestration. This is the only place that reads/writes `.txt` files.
- **Utils/**: Small, reusable helper functions used by several services.
- **Forms/**: Windows Forms UI files. They only call `Services` and render results.
- **Data/**: Store `.txt` files (human readable). Services read/write here.
- **Test Result/**: Store screenshots of the project's feature when working and copy of the `Data/` folder

Design rule: **UI → Services → Utils → Data → Test Result**. Forms must not access files directly and should not contain heavy logic.

## Root files

### `Program.cs`

- Entry point. Responsible for setting up visual styles and starting `MainForm`.
- Example minimal `Program.cs`:

```csharp
static class Program
{
    [STAThread]
    static void Main()
    {
        ApplicationConfiguration.Initialize();
        Application.Run(new MainForm());
    }
}
```

### `MainForm.cs` and `MainForm.Designer.cs`

- `MainForm.cs` holds basic navigation logic (open forms, show status). Keep it light.
- `MainForm.Designer.cs` is auto-generated by WinForms designer. Do not hand-edit the designer file.

## Folders and responsibilities

### `Models/`

**Purpose:** Hold data shapes (classes with properties) and no logic.

**Examples**:

- `Expense.cs`:

```csharp
public class Expense
{
    public string Id { get; set; }
    public DateTime Date { get; set; }
    public decimal Amount { get; set; }
    public string Currency { get; set; }
    public string Category { get; set; }
    public string Payer { get; set; }
    public string Tags { get; set; } // comma-separated tags
    public string ReceiptPath { get; set; }
}
```

- `User.cs` (minimal): holds user id, name, role
- `TaskItem.cs`, `Note.cs` similar: properties only.

**Rule:** No file I/O or heavy `if` logic here.

---

### `Services/`

**Purpose:** Hold core application logic. This is the single place that reads/writes `Data/*.txt` and transforms text to models.

**Typical services:**

- `ExpenseService.cs` — add/edit/delete expenses, compute totals, filters
- `BudgetService.cs` — per-category budgets, alerts, recommendations
- `FileStorageService.cs` — low-level reading/writing/parsing of `.txt`
- `ReminderService.cs` — check due tasks and raise notifications
- `CurrencyService.cs` — static exchange rates or conversion helpers

**Example usage from a Form**:

```csharp
var expenseSvc = new ExpenseService(new FileStorageService());
Expense e = new Expense { /* fill fields */ };
expenseSvc.AddExpense(e);
var monthlyTotal = expenseSvc.GetMonthlyTotal(2025, 12);
```

**Rule:** All file paths and parsing live in `FileStorageService`. Other services should call `FileStorageService` to persist data.

---

### `Utils/`

**Purpose:** Small reusable helpers that multiple services can use.

**Examples**:

- `FileHelper.cs` — `GetDataPath(string filename)`, `EnsureDataDirectory()`
- `DateHelper.cs` — `IsSameMonth(DateTime a, DateTime b)`
- `Validation.cs` — `IsPositive(decimal v)`, `IsValidCurrencyCode(string code)`

**Rule:** Keep methods small, unit-testable, and static when state isn't required.

---

### `Forms/`

**Purpose:** UI windows (WinForms). These should be purely presentation and call `Services` for work.

**Examples**:

- `ExpenseForm.cs` — Add/view/edit expense. On "Save" click it packages a `Models.Expense` and calls `ExpenseService.AddExpense()`.
- `FlowboardForm.cs` — List tasks and notes, create TaskItem objects and call `ReminderService`.
- `ToolsForm.cs` — Calculator and converters that call `Utils` or `CurrencyService`.

**Rule:** Avoid complex data parsing in forms. Do not read `.txt` directly in forms.

---

### `Data/`

**Purpose:** Contains raw storage files (human-readable `.txt`). Services read/write these files.

**Files and recommended formats:**

#### `expenses.txt`

One expense per line. Comma or pipe separated. Example (CSV-like):

```
Id|Date|Amount|Currency|Category|Payer|Tags|ReceiptPath
1|2025-12-01|250.50|USD|Office|Alice|office,stationery|Data/receipts/1.png
```

Implementation notes:

- Use `|` as a delimiter to avoid comma issues in descriptions.
- Escape or ensure no `|` inside fields.

#### `users.txt`

```
Id|Name|Role|Email
u1|Alice|Admin|alice@example.com
```

#### `tasks.txt`

```
Id|Title|DueDate|AssigneeId|Status|Tags|Note
t1|Prepare report|2025-12-30|u1|Open|report,finance|Draft due end of month
```

#### `notes.txt`

Simple format where each note is a block separated by `---` or one per line with ID and content.

**Rule:** Keep formats stable. If you change a format, update `FileStorageService` and commit a migration note in README.

---

### `Test Result/`

**Purpose:** Contains screenshots of working features per features developed and copy of `Data/` folder that holded the saved data when the feature was developed.

**Files and recommended formats:**

#### `Folders per feature`

every feature branch should have a folder designated in the `Test Result/` folder with it's own screenshots and copy of `Data/`.
> NOTE: the copy of `Data/` should be copied from the `bin` folder since C# puts the folder in the actual runtime!

## Example code snippets (using classes across folders)

```csharp
using TrackFlow.Models;

```

If `ExpenseService` is in the `TrackFlow.Services` namespace and `Expense` in `TrackFlow.Models`, you can instantiate and use them as shown earlier.

**Alias example (like Python import customtkinter as ctk):**

```csharp
using ES = TrackFlow.Services.ExpenseService;
```

## Namespaces, access modifiers and recommended patterns

### What a namespace is (simple explanation)

A **namespace** in C# is a way to group related classes together and avoid name conflicts. In this project, **namespaces mirror the folder structure**.

That means:

- Files inside `Models/` use `namespace TrackFlow.Models;`
- Files inside `Services/` use `namespace TrackFlow.Services;`
- Files inside `Forms/` use `namespace TrackFlow.Forms;`
- Files inside `Utils/` use `namespace TrackFlow.Utils;`

Think of a namespace like a full address for a class.

---

### Example 1: Declaring a namespace (inside a file)

**Models/Expense.cs**

```csharp
namespace TrackFlow.Models;

public class Expense
{
    public string Id { get; set; }
    public decimal Amount { get; set; }
}
```

This tells C#:
> "Expense belongs to TrackFlow.Models"

---

### Example 2: Using a namespace from another file

Now inside a service file:

**Services/ExpenseService.cs**

```csharp
using TrackFlow.Models;

namespace TrackFlow.Services;

public class ExpenseService
{
    public void AddExpense(Expense expense)
    {
        // use expense here
    }
}
```

What is happening:
- `using TrackFlow.Models;` imports all public classes in that namespace
- You can now directly use `Expense` without writing the full name

---

### Example 3: Using a service inside a Form

**Forms/ExpenseForm.cs**

```csharp
using TrackFlow.Models;
using TrackFlow.Services;

namespace TrackFlow.Forms;

public partial class ExpenseForm : Form
{
    private readonly ExpenseService _expenseService;

    public ExpenseForm()
    {
        InitializeComponent();
        _expenseService = new ExpenseService(new FileStorageService());
    }
}
```

Flow:
- Form → calls Service
- Service → uses Models
- Form never touches files directly

---

### Example 4: Using fully qualified names (no `using`)

You can also write the full namespace explicitly (not recommended for long-term use):

```csharp
TrackFlow.Models.Expense e = new TrackFlow.Models.Expense();
```

This works, but becomes painful fast. Prefer `using` statements.

---

### Example 5: Namespace alias (Python-style import)

This is closest to Python's:
`import something as x`

```csharp
using ES = TrackFlow.Services.ExpenseService;

ES service = new ES(new FileStorageService());
```

Useful when:
- Two classes have the same name
- You want shorter references

---

### Access modifiers (important rules)

- `public` → accessible from other folders/namespaces
- `internal` → accessible only inside TrackFlow
- `private` → accessible only inside the same class

Rules for this project:
- Models: `public`
- Services: `public`
- Helper methods: `public` or `internal`
- Form fields: usually `private`

---


- Use namespaces that match folder names: `TrackFlow.Models`, `TrackFlow.Services`, `TrackFlow.Forms`, etc.
- Public classes that are used by other layers should be `public`.
- Internal helper classes can be `internal` or `private` to limit access.
- Prefer constructor injection for services that need dependencies rather than using singletons.

Example:

```csharp
public class ExpenseService
{
    private readonly FileStorageService _storage;
    public ExpenseService(FileStorageService storage)
    {
        _storage = storage;
    }
}
```

## How to add a new feature (step-by-step)

1. Discuss scope with the team and write a short issue/PR (pull request) description.
2. Create a `feature/<short-name>` branch from `develop`.
3. Add a `Model` if needed in `Models/`.
4. Add logic into `Services/` (prefer adding unit tests if possible).
5. Use `FileStorageService` for any new persistent data format.
6. Add a new Form in `Forms/` only for UI elements.
7. Open a PR (pull request) to `develop` and request review from one teammate who owns the relevant module.

## Git workflow and branch rules

## Branches

1. **main**

   * The production-ready branch.
   * Only updated when features in `develop` are complete and tested.

2. **develop**

   * Active development branch.
   * All completed features are merged here first before going to `main`.

3. **feature/<name>**

   * Short-lived branches for individual features.
   * Created from `develop`.
   * Example: `feature/expense-form`.

---

## Step-by-Step Workflow

### 1. Clone the repository

```bash
git clone https://github.com/Blank-Creator-II/TrackFlow
cd TrackFlow
```

### 2. Check out `develop`

```bash
git checkout develop
git pull
```

* If you haven’t set tracking, run:

```bash
git branch --set-upstream-to=origin/develop develop
```

### 3. Create a feature branch

```bash
git checkout -b feature/<feature-name>
```

* Replace `<feature-name>` with a descriptive name.

### 4. Work locally

* Make changes in the correct folders (`Models/`, `Services/`, `Forms/`, `Utils/`).
* Stage and commit your changes:

```bash
git add .
git commit -m "Add <description of feature>"
```

### 5. Push your feature branch

```bash
git push -u origin feature/<feature-name>
```

* The `-u` flag sets upstream tracking for easier future pushes.

### 6. Keep your branch updated

Before merging your feature, sync with `develop`:

```bash
git checkout develop
git pull
git checkout feature/<feature-name>
git merge develop
```

* Resolve any conflicts if they arise, then push the updated branch.

### 7. Merge feature into `develop`

Once the feature is complete and tested:

```bash
git checkout develop
git merge feature/<feature-name>
git push
```

### 8. Merge `develop` into `main` (Release)

When `develop` contains stable and complete features:

```bash
git checkout main
git merge develop
git push
```

---

## Rules for the Team

1. Only `main` and `develop` are long-lived branches.
2. Every new feature must have its own `feature/<name>` branch.
3. Never commit directly to `main` or `develop`.
4. Always resolve conflicts locally before pushing.
5. Keep commits clear and descriptive.
